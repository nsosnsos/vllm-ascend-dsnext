一次 curl 的完整旅程

从 Router 端口进入，经代理与负载均衡，到 vLLM API Server、EngineCore、NPU Worker， 完成模型 forward 与采样，再经 reasoning / tool call 解析回到客户端。

代码基线：vLLM 6e448d0e，vLLM Ascend 当前分支，vLLM Router 当前 checkout。 行号对应当前工作区文件。

第 2、3 节是二选一的分支；第 4 节说明 Mooncake 的两套独立用法。 其余章节是两条分支共用的后续流程。

8

改写 prefill 请求

Router vllm_pd_router.rs:578 prepare_prefill_request

强制 max_tokens=1、stream=false，删除 stream_options，注入 kv_transfer_params。目的只算 KV，不生成正文。

9

发送 decode 请求

Router vllm_pd_router.rs:264 build_decode_kv_transfer_params

用 prefill 响应中的 connector 信息补齐 decode 的 kv_transfer_params， 保留客户端原始 stream 与 max_tokens，用相同 X-Request-Id 关联两段请求。

顺序模式

先等 prefill 返回 JSON，取到 kv_transfer_params 后再发 decode。 兼容性最好，TTFT 包含一次完整往返。

并发模式

NIXL push 或 MoRI-IO write 等场景下，tokio::join! 同时发两段请求， KV 身份来自启动时缓存的 bootstrap 信息。

PD 模式只把 decode 的响应回给客户端。 prefill 的 max_tokens=1 是 Router 内部改写，客户端不可见。

4. Mooncake 池化与传输

Mooncake 在本仓库里有两种完全不同的用法，配置和链路不能混：

形态connectorKV 存放位置适用场景
共享池（pooling） AscendStoreConnector
旧名 MooncakeConnectorStoreV1		 Mooncake 分布式存储池，按 block hash 键寻址 多实例共享前缀缓存；PD 与非 PD 都能用
直连 P2P MooncakeConnectorV1
（含 MooncakeHybridConnector）		 直接从 prefill 的 NPU 显存读到 decode 的 NPU 显存 PD 分离，一对一传输，不经过共享池
Router 的 --kv-connector mooncake 只负责给 PD 两阶段请求注入 kv_transfer_params（transfer_id、remote_bootstrap_addr、 remote_engine_id），它不参与 KV 的实际搬运。 真正的池化/传输都发生在 vLLM Worker 的 connector 里。

4.1 形态一：共享池（AscendStore + MooncakeBackend）

核心思想：把 KV cache block 当作内容寻址对象。key 由“模型 + 并行 rank + 前缀 block hash” 组成。任何实例先 lookup，命中就 get，未命中正常计算并在结束后 put。

10

connector 注册

Connector vllm_ascend/distributed/kv_transfer/__init__.py

插件启动时把 AscendStoreConnector 与兼容名 MooncakeConnectorStoreV1 注册进 KVConnectorFactory。 池后端由 backend 映射到 MooncakeBackend / MemcacheBackend / YuanrongBackend。

11

建立池连接

Connector backend/mooncake_backend.py _setup_store

读取 MOONCAKE_CONFIG_PATH 指向的 JSON，调用 MooncakeDistributedStore.setup(local_hostname, metadata_server, global_segment_size, local_buffer_size, protocol="ascend", rdma_devices, master_server_addr, engine)。global_segment_size 是本 rank 向池子贡献的显存大小。

12

调度侧查池

Scheduler pool_scheduler.py get_num_new_matched_tokens

按 block hash 生成 pool key，调用 store_scheduler.batch_is_exist(keys) 判断命中长度。命中则告诉 scheduler “这些 token 不用算”，并登记 load spec。

非 layerwise 路径下，EngineCore 不直接持有 store 连接，而是通过 LookupKeyClient 走 ZMQ REQ 到 rank 0 的 LookupKeyServer， 由后者执行 batch_is_exist 并回传命中 token 数；lookup_async 可让这一步不阻塞调度。

13

注册 KV 显存

Worker pool_worker.py register_kv_caches

把所有 KV cache 张量的 data_ptr() 与长度登记到传输引擎 （register_buffer）。之后 batch_copy 才能直接在显存与池之间搬运。

14

从池里拉取（load）

Worker kv_transfer.py KVCacheStoreRecvingThread

start_load_kv 把请求投递给接收线程，线程调用 m_store.get(keys, addrs, sizes)。Mooncake 后端对应 batch_get_into_multi_buffers，把池中数据直接写入已注册的 KV 显存。

15

写回池（save）

Worker kv_transfer.py KVCacheStoreSendingThread

请求结束后 save_kv_layer 投递保存任务。线程先 store.batch_is_exist(keys) 去重，再用 m_store.put(keys, addrs, sizes)（后端为 batch_put_from_multi_buffers）写入池，供其他实例复用。

池化 key 的构造在 metadata.py 的 PoolKey：

{cache_prefix}@{model_name}@tp_rank:{tp}@pcp{pcp}@dcp{dcp}@pp_rank:{pp}@group:{gid}@{chunk_hash}

chunk_hash 是前缀 block hash。相同前缀、相同并行切分的 block 在任何实例上都会得到同一个 key，这就是“跨实例前缀缓存共享”的来源。

配置示例

// mooncake.json —— 由 MOONCAKE_CONFIG_PATH 指向
{
  "metadata_server": "http://<metadata>:<port>",
  "master_server_address": "<master>:<port>",
  "protocol": "ascend",
  "device_name": "<rdma device>",
  "global_segment_size": "1GB",
  "local_buffer_size": "1GB",
  "preferred_segment": false,
  "prefer_alloc_in_same_node": true,
  "enable_ssd_offload": false,
  "tenant_id": "default"
}
vllm serve <model> \
  --kv-transfer-config '{
    "kv_connector": "AscendStoreConnector",
    "kv_role": "kv_both",

配置作用默认
backend池后端：mooncake / memcache / yuanrongmooncake
load_async拉取走后台线程，不阻塞 forwardtrue
enable_lookup是否允许该实例查池；纯写入实例可关闭以省 CPUtrue
save_decode_cache是否把 decode 增量也写池false
use_layerwise逐层传输。Mooncake 后端未实现 layerwise 协议，置 true 会静默降级为整块传输；该能力目前仅 memcache 后端具备false
cache_prefix多租户命名空间，避免相同 hash 冲突空

use_layerwise 的生效条件是后端声明了 layerwise 协议 （backend/__init__.py 的 layerwise_protocol 标记）。 目前只有 memcache 声明了该标记，因此 Mooncake 上置 true 会 use_layerwise_transfer=False，实际仍走整块 batch_copy。 另外 layerwise 查询从 block 0 开始，因为它不与本地 prefix cache 对齐。

池化路径的失败语义

事件行为
lookup 超时或 master 不可达返回全 miss，请求退化为正常计算，不报错
get 部分 key 失败失败 block 记入 invalid_block_ids，由 scheduler 重算
put 部分 key 失败记日志并继续；只影响后续命中率，不影响当前请求正确性
key 不存在batch_get_into_multi_buffers 返回负错误码，按 miss 处理

4.2 形态二：直连 P2P（MooncakeConnectorV1）

PD 分离下，prefill 算完 KV 不落池，而是通过 Mooncake TransferEngine 直接从 prefill 显存读到 decode 显存。Router 负责把两段请求串起来。

两侧都调用 global_te.register_buffer(ptrs, lengths) 把 KV 显存 注册给 TransferEngine，并通过 ZMQ handshake 端口交换 kv_caches_base_addr、te_rpc_port、 block_strides 等元数据。

20

真正搬运

Worker _transfer_kv_cache_all_groups

decode 侧按 transfer_id 找到远端 metadata，计算每 layer 的源/目标地址 与长度，调用 TransferEngine 的 batch_transfer_sync_read(session_id, src, dst, length)： decode 主动从 prefill 远端显存拉取，写入本地 KV block。 完成后通过握手通道回 done 信号，释放远端端口计数。

与池化的关键差异

维度AscendStore（池化）MooncakeConnectorV1（直连）
寻址block hash → pool keytransfer_id + remote engine id
生命周期数据留在池里，可被任意后续请求命中一次请求一次传输，用完即弃
是否依赖 Router不依赖；单实例也能用依赖 Router 注入 kv_transfer_params
典型角色kv_both / kv_producer / kv_consumerprefill=kv_producer，decode=kv_consumer
握手通过 metadata / master serverZMQ handshake + bootstrap server
传输 APIbatch_put_from_multi_buffers / batch_get_into_multi_buffersbatch_transfer_sync_read
不要在 PD 分离场景里同时配 MooncakeConnectorV1 与 AscendStoreConnector 去搬同一份 KV：前者按 transfer_id 点对点搬， 后者按 hash 写池，会产生重复流量，且 decode 可能拿到不一致的来源。 需要“PD + 跨实例缓存复用”时，用 AscendStoreConnector 的 kv_producer/kv_consumer 角色，让两边都走池。

13.2 数据结构流转

curl JSON
  → ChatCompletionRequest (Router, serde)
  → ChatCompletionRequest (vLLM, Pydantic)
  → EngineInput                (render + tokenize)
  → EngineCoreRequest          (ZMQ, 含 data_parallel_rank)
  → SchedulerOutput            (本步 batch 与 KV block)
  → input_ids / attn_metadata  (NPU 张量)
  → hidden_states → logits
  → SamplerOutput → ModelRunnerOutput
  → EngineCoreOutput → EngineCoreOutputs
  → RequestOutput              (detokenize 后)
  → DeltaMessage / ChatMessage (reasoning + tool call)
  → ChatCompletionResponse / SSE chunk
  → curl

13.3 最短心智模型

  1. Router 决定“谁来做”：一次转发，或 prefill + decode 两次。
  2. API Server 决定“怎么问”：模板、token、sampling、grammar。
  3. EngineCore 决定“这一秒算哪些 token”：batch、KV block、调度顺序。
  4. Worker 决定“怎么算”：张量布局、attention backend、ACLGraph replay。
  5. Mooncake 决定“KV 放哪、怎么搬”：共享池按 hash 存取，直连按 transfer_id 拉取。
  6. Parser 决定“怎么讲”：reasoning 与 content 分离，tool call 结构化。
